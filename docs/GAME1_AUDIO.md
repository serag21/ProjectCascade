# SPARK STAMPEDE — original audio production

## Status and provenance

All audio in `assets/audio/` is **original, generated by `tools/generate_audio.py`, no third-party samples**. The generator uses only Python standard-library math, seeded `random` noise and `wave` PCM encoding. No samples, sound fonts, MIDI files, loops, music quotations, purchased or downloaded audio, external composers or audio libraries are used. Every melody, chord voicing, rhythm and synthesis parameter is written in the generator.

There are two generations:

| Set | Created | Files | Notes |
| --- | --- | --- | --- |
| Legacy | 2026-10-25, Python 3.14.2 on Windows | 6 (catch, bank, dash, upgrade, round_reward, `pop_meadow_loop`) | Generator code unchanged. Regenerated on 2026-11-05 under Linux/Python 3.13.18, the bytes were identical to the original manifest hashes. Kept for provenance. |
| 2026-11 extension | 2026-11-05, Python 3.13.18 on Linux | 15 cues + 3 arena loops + 3 FINALE layers | Cues are 44.1 kHz mono. Music is 22.05 kHz: base loops are stereo, finale layers are mono. |

**Nothing has been uploaded to Roblox, given an asset ID, heard in Studio or approved by a listener.** Every `id` in `game/ReplicatedStorage/Spark/AudioCatalog.luau` is still empty. Until uploads, experience permissions and engine playback are tested, these files must not be called live game audio. The numbers below come from waveform analysis. They do not certify how anything sounds, how loud it feels, or how it plays on Roblox. Built-in `fallback` cues are placeholders and are separate from these originals.

A finale layer is meant to play **on top of** its base loop. Both files have exactly the same sample count, tempo and bar grid, and a layer is never played on its own. Each loop is a whole number of 4/4 bars with an integer frame count. Every note tail, echo, filter and limiter is computed circularly, so the loop wraps into its own start. Verify measures the wrap step against the 64 neighbouring steps. The seam ratio is ≤ 0.2 for every new file, where 1.0 means "typical neighbour" and a click would be well above 1.5.

## Loudness and safety method

All measurements come from the decoded 16-bit PCM. They are **unweighted RMS and sample peak, not LUFS/K-weighted loudness**, and no listening test is involved.

- **Peaks:** no file, and no base+finale sum, may exceed -1 dBFS. The writer refuses to produce anything hotter. Cues are normalized to per-cue peaks between -3.5 and -9 dBFS. Sustained tones (countdown, whistle) and the UI tick sit lower, because a steady tone sounds louder than a percussive cue with the same peak.
- **Reference:** the median peak of the 15 new cues, which is **-5.00 dBFS**.
- **Music level:** each base loop masters to RMS = reference - 8.7 dB, which is **-13.69 dBFS**. Base+finale, summed per channel with the mono layer on both channels, masters to reference - 7.5 dB, which is **-12.49 dBFS**. Both fall inside the requested 6–9 dB window, and verify enforces that window. Bringing in the finale raises level by about 1.2 dB. Most of the intensity comes from density: a kick on every beat, 16th arps and stabs.
- **Mastering stage:** each stem is first scaled to a measured relative RMS. Percussion stems get gentle tanh drive, and bass and pads are ducked sidechain-style at each kick. One smooth, circular gain curve with an ~8 ms look-ahead is then computed from the worst of |base|, |finale| and |base+finale|, and applied to both files. Its ceiling is -1.5 dBFS, below the -1 dBFS rule. Gain reduction measured at generation:

  | Arena | Max reduction | Mean reduction when active | Share of samples limited |
  | --- | ---: | ---: | ---: |
  | Meadow | 3.79 dB | 0.83 dB | 21% |
  | Canyon | 4.24 dB | 0.98 dB | 34% |
  | Aurora | 3.84 dB | 0.62 dB | 17% |

- **No harsh treble:** every new file passes through a Butterworth low-pass: 4th-order at 9 kHz for cues, 8.5 kHz for music. Music also benefits from the 22.05 kHz rate, whose Nyquist limit is 11.025 kHz. Additive voices drop any partial above 8 kHz. Verify applies a 4th-order 10 kHz high-pass and requires that the energy above 10 kHz sit at least **30 dB** below full-band energy. Measured values range from -36.3 dB (`gate_open`, airy noise swell) down to -85 dB.
- **DC and edges:** new files must have |mean| < 0.002 full scale. Cues start and end within 50 LSB of zero. A 30 Hz high-pass, or 45 Hz for the rumble, removes sub-bass boom and DC.
- **Lengths:** cues ≤ 2 s, rumble ≤ 3 s, loops 16–24 s with the exact bar-grid frame count.
- **Catalog volumes:** these are authoring defaults. At the catalog `volume` values, new cue peaks land between about -12.9 and -19.5 dB, with a median of -16.1 dB. That is the same range as the legacy cues (-12.3 to -21.8 dB). The arena loops use `volume=0.28`, which keeps the same 8.7 dB (base) and 7.5 dB (base+finale) gaps in game. **This is about 12 dB louder in game than the legacy `music` entry**: `pop_meadow_loop` at 0.22 sits about 21 dB under the cues. If playtests find the music too present, turn down the `music_*` volumes. Leave the files alone, because the mastering targets assume equal base and finale volumes.

Kid-friendly direction: rounded bells, mallets and e-piano, a soft kick, no sirens, no harsh buzz or strobing amplitude, and no sudden loud transients. The zap is a cartoon descending wobble, and the buzzer is a warm major-chord horn rather than a rasp.

## Integration notes for the client

- Cue keys: `zap`, `pop`, `gate_open`, `golden_spawn`, `golden_catch`, `stampede_rumble`, `chain_tier`, `countdown`, `start_whistle`, `buzzer`, `rank_up`, `ui_click`, `ui_claim`, `signature`, `starstruck`. The legacy keys are kept. `ui` now references `ui_click.wav`, and `zap` and `pop` reference their new originals. All their built-in fallbacks are kept.
- Music: `music_meadow`, `music_canyon` and `music_aurora` each name their layer through `finale="music_<arena>_finale"`, and the layer points back with `layerOf`. Start a base loop and its finale layer together, with the finale at volume 0. When fading the finale in (for example at 85 s), copy the base `TimePosition` to the finale first, so the two stay in phase. Crossfade between arenas on the base loops. All six music entries carry `looped=true`, `bpm` and `bars`.
- `fallbackSpeed` (bank, dash, round_reward, zap, pop) only fits the built-in placeholder. The current client (`Effects.sound`) applies it even when an uploaded `id` is used. That must change before IDs are filled, or the originals will play at the wrong pitch and speed.

## Owner upload steps

The generator cannot do this step: it needs the owner's Roblox account. Roblox's audio-upload limits, monthly quota and moderation rules change over time. Check them in the current Roblox Creator documentation; this session could not reach create.roblox.com.

1. In Studio, open the Spark Stampede place and go to **View → Asset Manager**. Use **Import / Bulk Import** to select the WAVs in `assets/audio/` that you want to use. The cue, arena and finale files are listed above, and `pop_meadow_loop.wav` is optional. Upload them under the account or group that owns the experience.
2. Once each upload is processed and moderated, right-click it in Asset Manager (Audio) and choose **Copy Asset ID**.
3. Save the IDs as JSON keyed by catalog key, for example `ids.json`:
   ```json
   {"catch": 1234567, "zap": 2345678, "ui_click": 3456789, "music_meadow": 4567890, "music_meadow_finale": 5678901}
   ```
   One upload per WAV is enough. Entries that share a file, such as `ui` and `ui_click`, are filled automatically.
4. Preview the change, then apply it:
   ```bash
   python tools/set_audio_ids.py ids.json --dry-run
   python tools/set_audio_ids.py ids.json
   .tools/luau/luau-compile --null game/ReplicatedStorage/Spark/AudioCatalog.luau
   python tools/generate_audio.py --verify
   ```
   The tool rewrites only `id="..."` fields and leaves every other byte alone. It writes nothing if the input contains unknown keys, non-positive or non-integer IDs, duplicate JSON keys, one ID used for two different WAVs, or an ID that would overwrite an existing different one (pass `--replace` to allow that).
5. Make sure the experience has permission to use each asset, then sync the catalog into Studio as usual.

## Reproduction and verification

From the repository root:

```bash
python tools/generate_audio.py              # renders all 27 WAVs (~45 s) and writes the manifest after all checks pass
python tools/generate_audio.py --verify     # read-only (~4 s): format, peaks, clipping, DC, >10 kHz energy,
                                            # cue lengths/edges, loop frame count + seam, base+finale headroom and
                                            # level gap, catalog keys/files/durations/finale links, budget, manifest SHA-256
python tools/generate_audio.py --reproduce  # renders into a temp folder and requires byte-identical files
python tests/test_set_audio_ids.py          # ID tool: rewrite, sharing, dry-run, --replace, refusals, compile
python tests/test_audio_pipeline.py         # verifier negatives: seam click, treble, DC/clip/edge, limiter bound
.tools/luau/luau-compile --null game/ReplicatedStorage/Spark/AudioCatalog.luau
```

Observed on 2026-11-05, Linux 6.18 with Python 3.13.18 and the repo's Luau compiler:

- Generation and `--verify` passed 412 checks.
- `--reproduce` regenerated all 27 WAVs byte-for-byte.
- The six legacy files matched their 2026-10-25 hashes.
- Both test files passed (11 + 4 tests), and AudioCatalog compiled.
- Tampering with one manifest hash made `--verify` exit 1.

On a different platform, `math` library differences can change the last quantization bit. If that happens, inspect the result and regenerate the manifest deliberately. Progress messages go to stderr. Stdout carries only the manifest JSON and a final `PASS:` line, which `tools/run_checks.ps1` parses.
